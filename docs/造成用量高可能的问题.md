# 造成云函数 / 云对象用量高可能的问题

> 审查日期：2026-05-01  
> 审查范围：`App.vue`、首页抽餐链路、`utils/app-state.js`、`utils/cloud.js`、`co-user`、`co-campus`、`co-ai`、饭堂详情页。

## 当前结论

这次已经处理几个最容易放大调用量的点：

1. 抽餐后的 `state` 和 `history` 不再分别同步，而是合并成一次 `co-user.syncAppData()`。
2. 首页抽餐后不再自动调用 AI，用户需要主动点击“让 AI 再挑一次”才会触发 `co-ai.pickDishFromCandidates()`。
3. `co-campus` 读缓存从 60 秒提升到 5 分钟。
4. 首页菜品池前端缓存从 5 分钟提升到 10 分钟。
5. 饭堂详情和档口详情增加 45 秒页面级缓存，管理写操作后仍强制刷新。
6. `utils/app-state.js` 里剩余几个直接 `uniCloud.importObject('co-campus')` 的读调用已收敛到 `utils/cloud.js`。

所以现在用户点击一次“吃什么”的云调用量大致变成：

- 菜品池缓存命中：只会产生一次延迟合并同步，也就是 `co-user.syncAppData()`。
- 菜品池缓存未命中：会先请求一次 `co-campus` 菜品候选池，再产生一次 `co-user.syncAppData()`。
- 用户额外点击 AI：才会额外请求一次 `co-ai.pickDishFromCandidates()`。

这比之前“抽餐 + 自动 AI + state 同步 + history 同步”的链路轻很多。

## 已修复 1：抽餐后的 state/history 分开同步

风险等级：已修复，原风险为严重

相关位置：

- `utils/app-state.js`
- `utils/cloud.js`
- `uniCloud-aliyun/cloudfunctions/co-user/index.obj.js`

原问题：

抽餐会同时改变两个本地数据：

- `state.daily.remaining`
- `state.daily.lastResult`
- `state.stats.servedCount`
- `historyList`

如果分别调用 `cloudSyncState()` 和 `cloudSyncHistory()`，一次抽餐就可能产生两次 `co-user` 写调用。AI 结果返回后再更新最新记录，又可能追加一次同步。

本次修复：

- 新增 `co-user.syncAppData(token, payload)`。
- 新增前端封装 `cloudSyncAppData(token, payload)`。
- 新增 `syncAppDataToCloud(stateData, historyList)`，统一做 3 秒防抖。
- `drawMealResult()` 和 `drawMealResultAsync()` 都改为先本地写入，再合并同步。
- `updateLatestMealResult()` 在更新最新抽餐结果时，也走合并同步。

现在效果：

- 一次抽餐后，`state` 和 `history` 合并为一次云对象调用。
- 短时间连续抽餐时，只同步最后一次合并数据。
- 本地体验不被云端失败阻塞。

仍需注意：

- 其他非抽餐场景如果单独调用 `saveAppState()` 或 `saveHistoryList()`，仍可能走原来的单项同步。这是合理保留，因为不是所有状态变更都同时需要同步 history。

## 已修复 2：首页 AI 从自动触发改为用户主动触发

风险等级：已修复，原风险为严重

相关位置：

- `pages/index/index.vue`
- `utils/app-state.js`
- `uniCloud-aliyun/cloudfunctions/co-ai/index.obj.js`

原问题：

用户点击“吃什么”后，页面会自动调用：

```js
aiPickFromCandidates(...)
```

这意味着每次普通抽餐都会额外触发一次 `co-ai.pickDishFromCandidates()`。AI 调用比普通数据库读写更贵，也更容易被免费额度或限流影响。

本次修复：

- 抽餐后先展示模板推荐结果。
- 弹窗内新增“让 AI 再挑一次”按钮。
- 只有用户主动点击按钮时，才调用 `aiPickFromCandidates()`。
- AI 成功后会标记 `isAI: true`，避免同一个结果反复展示 AI 按钮。

现在效果：

- 只想快速抽餐的用户不会消耗 AI 调用。
- AI 变成一个明确的增值动作，调用量更可控。
- `co-ai` 原有每日数据库用量统计仍然保留。

仍需注意：

- `co-ai` 里分钟级限流仍使用内存变量 `userCallLog`，冷启动或多实例时不够严格。
- 每日 AI 总次数目前已有数据库记录 `eat-what-ai-usage`，比纯内存可靠。
- 如果上线后 AI 成本仍高，可以把后台配置里的 `dailyLimit` 调低，例如从 5 调到 2 或 3。

## 已修复 3：co-campus 读缓存 TTL 只有 60 秒

风险等级：已修复，原风险为中等

相关位置：

- `uniCloud-aliyun/cloudfunctions/co-campus/index.obj.js`

涉及配置：

原配置：

```js
const READ_CACHE_TTL = 60 * 1000
```

当前配置：

```js
const READ_CACHE_TTL = 5 * 60 * 1000
```

涉及接口：

- `getApprovedCampuses()`
- `getCanteensByCampus()`
- `getStallsByCanteen()`
- `getNormalDishCandidates()`
- `getCampusDishCandidates()`

问题说明：

饭堂、档口、菜品候选池属于低频变化数据，但云对象内存缓存只有 60 秒。用户停留时间稍长，或者开发时频繁刷新，就容易重新查数据库。

为什么会影响调用量：

- 首页抽餐第一次未命中前端缓存时，会请求候选菜品池。
- 饭堂详情页重新进入或返回时，可能请求档口列表。
- 60 秒过期后，即使数据没有变化，也会重新打到数据库。

本次修复：

- 已把 `READ_CACHE_TTL` 提升到 5 分钟。
- 现有管理员新增、编辑、删除档口/菜品后，已经调用 `clearReadCache()` 清理读缓存。
- 审核校园入驻后也会清理读缓存。

## 已修复 4：饭堂详情页返回时仍会刷新档口列表

风险等级：已修复，原风险为中等

相关位置：

- `pages/canteen/detail.vue`

原逻辑：

- `onLoad()` 会请求一次 `loadStalls()`。
- 首次 `onShow()` 已用 `skipNextShow` 跳过。
- 后续从档口页面返回时，会再次调用 `loadStalls()`。

问题说明：

这个逻辑比“每次 onShow 都刷新”已经好很多，但如果用户频繁在饭堂详情和档口详情之间来回，仍会产生重复 `co-campus.getStallsByCanteen()` 调用。

为什么会影响调用量：

- 每次返回详情页都可能重新请求完整档口 + 菜品列表。
- 档口列表通常不需要秒级刷新。

本次修复：

- `pages/canteen/detail.vue` 增加 `STALL_REFRESH_TTL = 45 * 1000`。
- 45 秒内返回饭堂详情页，如果已有档口数据，不再重复请求。
- 新增、编辑、删除档口后调用 `refreshStalls()`，仍然强制刷新，保证管理操作后能看到最新数据。

额外补充：

- `pages/canteen/stall.vue` 也增加了 `DISH_REFRESH_TTL = 45 * 1000`。
- 新增、编辑、删除菜品后调用 `refreshDishes()` 强制刷新。
- 菜品写操作会写入 `eat-what-stall-dirty` 标记；返回饭堂详情页时如果检测到该饭堂被改过，会绕过 45 秒缓存强制刷新。

## 风险 3：AI 分钟级限流仍是内存变量

风险等级：中等

相关位置：

- `uniCloud-aliyun/cloudfunctions/co-ai/index.obj.js`

涉及变量：

```js
const userCallLog = {}
```

问题说明：

`userCallLog` 是云函数实例内存变量。它能挡住同一个热实例内的短时间重复调用，但不能保证跨冷启动、跨实例完全一致。

为什么会影响调用量：

- 云函数冷启动后，内存限流记录会丢失。
- 如果云函数有多个实例，同一个用户打到不同实例时，分钟限流可能不一致。

当前缓解：

- 每日 AI 调用已有 `eat-what-ai-usage` 数据库记录。
- 首页 AI 已改为用户主动触发，默认抽餐不再自动消耗 AI。

建议修复：

- 如果 AI 调用量继续偏高，把分钟级限流也持久化到数据库或 Redis 类服务。
- 或者先保持每日数据库限额，把 `dailyLimit` 调低到 2 到 3。

## 已修复 5：前端菜单缓存只有 5 分钟

风险等级：已修复，原风险为中低

相关位置：

- `utils/app-state.js`

原配置：

```js
const MENU_CACHE_TTL = 1000 * 60 * 5
```

当前配置：

```js
const MENU_CACHE_TTL = 1000 * 60 * 10
```

问题说明：

首页抽餐会通过 `fetchNormalFoodPool()` 或 `fetchCampusFoodPool()` 获取候选菜品池。当前前端缓存 5 分钟，已经能挡住短时间重复抽餐，但如果用户停留时间较长，仍会重新请求。

为什么会影响调用量：

- 用户打开首页后，首次抽餐会拉候选池。
- 5 分钟后再次抽餐，可能重新请求 `co-campus`。

本次修复：

- 已把前端菜单缓存从 5 分钟提升到 10 分钟。
- 首页连续抽餐更容易命中前端缓存，减少 `co-campus` 候选菜品池请求。

## 已修复 6：`utils/app-state.js` 里仍有少量直接 import 云对象

风险等级：已修复，原风险为低

相关位置：

- `utils/app-state.js`

涉及方法：

- `fetchCloudCanteens(campusName)`
- `fetchCloudStalls(canteenId, forceRefresh)`
- `fetchCanteenFullData(campusName)`

原问题：

项目规范里要求云对象调用统一通过 `utils/cloud.js`。当前大部分已经走 `utils/cloud.js`，但这几个方法内部仍直接：

```js
uniCloud.importObject('co-campus')
```

为什么会影响调用量：

- 这本身不会直接增加调用量。
- 但调用入口分散后，不利于统一做缓存、限流、降级和日志统计。

本次修复：

- 新增 `cloudGetCanteensByCampus(campusName)`。
- 新增 `cloudGetCanteenFullData(campusName)`。
- `fetchCloudCanteens()`、`fetchCloudStalls()`、`fetchCanteenFullData()` 已改为通过 `utils/cloud.js` 调用。
- 后续如果要做统一日志、缓存策略或降级处理，可以集中在 `utils/cloud.js` 做。

## 已排除的旧风险

下面这些旧判断在当前代码里不准确，不应继续按严重风险处理：

1. `App.onShow()` 调用 `ensureAppState()` 会产生云同步  
   当前 `ensureAppState()` 只读写本地 storage，不会直接调用云对象。

2. `pages/campus/select.vue onShow()` 会请求云端校园列表  
   当前 `refreshPage()` 使用 `getCampusList()`，主要来自本地预置和本地申请记录，不会直接请求云端。

3. 所有页面 `onShow()` 都会触发云调用  
   当前不是所有页面都会这样。真正需要关注的是饭堂详情页、饭堂/菜品数据页、以及用户主动触发的抽餐和 AI。

1. 已完成：抽餐后 `state/history` 合并同步。
2. 已完成：首页 AI 改为用户主动触发。
3. 已完成：把 `co-campus` 的 `READ_CACHE_TTL` 从 60 秒提升到 5 分钟。
4. 已完成：给饭堂详情和档口详情增加 45 秒页面级缓存。
5. 已完成：把 `utils/app-state.js` 里剩余直接 `uniCloud.importObject('co-campus')` 的读调用收敛进 `utils/cloud.js`。
